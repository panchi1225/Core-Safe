# 発行済みQRの最新会社一覧・送信時の会社自動登録

公開アンケートは有効なtoken設定を確認した後、会社名だけの共通一覧 `publicNewcomerCompanyMaster/general.contractorOptions` をサーバーから取得する。QRのURL・token・現場・作業所長・期限は維持するため、印刷済みの期限内token QRを再印刷する必要はない。匿名からの社内マスター・社員情報・回答の読取りは許可しない。共通一覧は会社名だけを公開する単一getで、他フィールドやコレクション一覧は公開しない。

## 動作例

1. 社員が会社マスターへ「A建設」を追加して保存すると、既存の各現場QRから「A建設」を選択できる。
2. 作業員が「その他（手入力）」へ「B工業」を入力して送信すると、回答・会社マスターへの追加・共通会社一覧への追加を同一バッチで保存する。次に同じQRまたは別現場の既存QRを開いた回答者は「B工業」を選べる。
3. 2人が同時に「B工業」を送っても `arrayUnion` によって1社だけ登録する。別会社の同時送信も消失させない。前後の空白は除去するが、略称や表記ゆれを推測して別会社と統合しない。

会社名変更・削除も共通一覧へ反映する。提出済み回答は変更しない。既に開いている画面をリアルタイム更新する機能ではなく、QRを読み直すか画面を再読込みした際に最新になる。

## 書込みの保護

手入力の会社登録は、今回新規作成する有効QRの回答と同一の原子バッチに限定する。社内マスターに許可する変更は `contractors` への当該1社の追加と非公開の関連回答IDだけ。他項目の変更、既存会社の削除、回答の再利用、架空の回答ID、異なる会社の追加は拒否する。共通一覧は変更後の会社マスターと完全一致しなければ保存できない。

署名・現場情報等の回答検証または会社登録に失敗すると全操作が取り消され、回答だけ保存済みになることはない。会社名200文字・会社候補300件の既存上限を維持する。上限時は回答と追加の両方が失敗するので、社員がマスターを整理してから再送信する。

社員が会社マスターを編集中に手入力の新会社が届いた場合、編集開始時には存在しなかった会社をトランザクションで引き継ぎ、古い画面からの保存による消失を防ぐ。社員の会社マスター保存と共通一覧保存は同一トランザクション。QR設定内の旧会社一覧も100件ずつ同期して既存の読取り方式との互換性を維持する。この旧一覧の同期が中断した場合は再保存またはQR管理画面を開き直すことで復旧できる。共通一覧は先に原子的に更新済みのため、新画面の会社選択は最新を参照できる。

## 本番反映手順

1. 現行本番Rules・main・gh-pagesの状態を記録する。新Rulesの匿名社内読取拒否・回答検証・会社追加制限をEmulatorで検証する。
2. 対象 `core-safe` の `firestore.rules` だけを反映する。課金、Cloud Functions、Cloud Run、Cloudflare Worker/D1、社員自動入力の設定は変更しない。
3. 現行会社マスターから会社名だけの共通一覧を初期化する。既存の会社名は社員用同期処理 `syncPublicNewcomerContractors()` が整理・コピーする。初期化前の匿名送信は自動登録を完了できないため、公開フロント切替前にこの工程を終える。
4. PR CI成功後にmerge、main push CI成功を確認する。公開中の社員自動入力URLを維持して検証済みmainをbuildし、GitHub Pagesへ公開する。現在の設定値は `VITE_PUBLIC_AUTOFILL_URL=https://core-safe-public-autofill.paaaaanchi1225.workers.dev`。他の公開機能を無効化する空の設定でbuildしない。
5. 本番の既存QRで会社一覧を確認する。匿名の会社マスター・社員・回答の読取や会社一覧への単独変更が拒否されることを確認する。実回答を試験用に送信して業務データを汚さない。

本番反映結果と未完了工程は作業完了時に報告する。コードのmergeだけでRules・共通一覧・Pagesの反映完了と扱わない。
